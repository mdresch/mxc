# Root-Cause Log — why each real policy got built

Append-only, like every other log in this methodology. One entry per *new* `agent_learning` TaskPolicy any project built using this template — not what the policy does (that's in its own definition), but **what real, repeating judgment call it existed to catch, and what it looked like before the policy existed.**

This is the template's own lessons-learned mechanism. It exists because the first version of this template could only name 6-7 policies — the ones already evidenced by the time ADPA and SocialEngage had each independently built them. The real number any given project ends up needing is not fixed, and should not be guessed ahead of evidence (see §4.6 of this template's own `sequence-and-lessons.md`). What *is* reusable, across every project, is the **shape of the trigger** — recognizing "this is the kind of moment that tends to need a new policy" earlier than last time, without ever pre-building the policy itself before a real case exists.

## Entries

### `classify-audit-finding` (ADPA)
**Trigger, concretely:** a sample-ADR audit against real code needed a stable verdict taxonomy (confirmed_accurate / confirmed_with_drift / partially_confirmed / contradicted / stale_superseded / unauditable / flag_for_human_review) — before this existed, audit findings were ad hoc prose verdicts, re-derived differently each time.
**Root cause, generalized:** a project has a *repeating* classification decision (not a one-off) once it has run the same kind of check against reality more than once and the verdict categories have stabilized. One real finding (AUDIT-001) was enough to justify building it — the policy was built *because* a second real audit was about to happen, not in anticipation of a first.

### `validate-plan-dependency` (ADPA)
**Trigger, concretely:** four real cases of "is Plan B's finalization actually justified by Plan A's real output yet, or would finalizing now mean asserting rather than deriving it" had already happened (PM subsidiary-plan sequencing) before this was built.
**Root cause, generalized:** a *gating* decision (proceed / partially proceed / block / escalate), as distinct from a *classification* decision — recognized by asking "does finalizing X right now require pretending Y already has real output it doesn't have yet." Four real near-misses, not one, triggered this — a gating policy seems to need a slightly higher evidence bar than a classification one before it's worth building, though that's one data point, not a rule.

### `approve-adr` / `approve-brd` / `approve-fdd` / `approve-user-stories` (ADPA, converged independently with SocialEngage's `approve-adr`/`approve-brd`/`approve-fdd`/`approve-story`)
**Trigger, concretely:** the first real ADR (ADR-030) needed an explicit accept/reject/revise decision, and ADPA's own standing governance rule (the project's human sponsor must directly sign off) meant the decision couldn't just be reasoned about once and forgotten — it needed a *recorded*, repeatable shape.
**Root cause, generalized:** any artifact type that (a) has a real human-approval requirement and (b) recurs (more than one ADR will ever be written) earns this shape. The four sibling policies are four instances of literally the same shape (approve / reject / request-revision-before-decision) at four rungs of the same traceability chain — once the first one (ADR) is justified, the other three usually are too, by the same reasoning, not by separate evidence each time. **Real divergence found, not yet resolved:** SocialEngage's own Story-level policy uses a different action set (`mark_ready`/`mark_blocked`/`request_revision_before_decision`) than ADPA's (`approve_user_stories`/`reject_user_stories`/`request_revision_before_decision`) for what is conceptually the same decision. Two independent real builds did not converge here the way they did on `approve-adr`/`approve-brd`/`approve-fdd`. Noted as an open question for whichever real case comes third, not resolved by picking one now.

### `validate-intent-foundation` (ADPA, converged independently with SocialEngage's `socialengage-pipeline`/`validate-intent-foundation`)
**Trigger, concretely:** stories started reaching "Accepted ADR + Accepted BRD/FDD + drafted AC" state without any check for whether that was actually *enough* to start real code work — a distinct question from whether the BRD/FDD content itself was good (that's the approve-chain's job).
**Root cause, generalized:** once a project has a real multi-stage document chain (ADR→BRD→FDD→Story) feeding into a real code-implementation loop (`implement-story`), the seam between "the paperwork is approved" and "it's safe to start building" is a real, separate decision — not automatically true just because every upstream document was individually approved. SocialEngage's own history is the strongest evidence here: a *learned*, low-authority version of this exact decision hit a hard entropy ceiling (~42% probability) on real positive-only data and could never statistically earn autonomy — this decision needs `full` authority, reasoned per instance, not learned from aggregate stats. That finding transfers directly; don't re-attempt a learned version of this one.

### `classify-hypothesis-status` (`agent-learning-governance` — literally shared, not independently re-converged, across agent-learning and SocialEngage)
**Trigger, concretely:** a Hypothesis (the stage before Requirement/ADR) needed a stable status taxonomy (advance_to_testing / mark_validated / mark_invalidated / mark_inconclusive / remain_formulated_blocked / flag_for_human_review) as real hypotheses started accumulating dated test-outcome updates.
**Root cause, generalized:** this is the one policy in this log that is *literally the same `agent_id`/`task_id`* across two real codebases, not a parallel independent build. That's a stronger signal than convergence — it suggests this specific decision belongs at the SDK/methodology level, not re-namespaced per project. Template takeaway: when a decision shape turns out to be genuinely cross-project (not just similar), consider whether it should live under a shared namespace rather than being re-declared per project.

## What this log is *not* for

Not a place to pre-guess a project's 8th or 9th policy before it has a real case. Not a place to record a policy's actual decisions (that's the real episode store). This log only grows when a *new* policy shape actually gets built somewhere real — ADPA needing another one, a future project needing one neither ADPA nor SocialEngage ever did, or the `approve-user-stories`-vs-`approve-story` divergence above finally getting resolved by a real third case. If nothing new has happened, this file doesn't change — that's a correct, reportable state, not a gap to fill.
