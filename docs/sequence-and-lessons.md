# Sequence & Lessons — order that actually mattered, confirmed the hard way

Every rule below was learned by hitting it, not derived in the abstract. Cited against the real projects (ADPA, SocialEngage, Enterprise Work Hierarchy) that surfaced it, so a future reader can go check the primary source rather than trust this summary alone.

---

## 1. Governance-document order

1. **Spark → Ideation → Business Case → Benefits Statement → Charter.** Benefits Statement before Charter, not after — PMBOK 8 confirms the Benefits Plan is a Charter *input*, not a follow-on (ADPA, corrected after an earlier draft had them in the wrong order).
2. **Charter before the Pillars Exercise before the 9 subsidiary management plans.** Obvious in principle; the real trap is treating the Charter as a PMP (Project Management Plan) — it isn't one. The PMP is an *integration* document, built only after every subsidiary plan is grounded in concrete work packages. Don't draft a PMP early thinking it's the Charter's natural next step.
3. **Pillars Exercise bridges Charter to Architecture.** Right after the Project Charter is approved, execute the **Pillars Exercise** (`docs/07-architecture/PILLARS-EXERCISE.md`) to decompose the project into 4–6 mutually exclusive, collectively exhaustive architectural and functional pillars.
4. **100% ADR Pillar Coverage Invariant.** For each identified pillar, draft high-level foundational ADRs. The set of initial ADRs must provide 100% full coverage across every identified pillar before proceeding to requirements. No architectural pillar may be left floating or unassigned.
5. **Hypothesis before Requirement.** A Hypothesis (falsifiable design assumption) gets tested and its status updated *before* it becomes an ADR (a Requirement-stage artifact). `classify-hypothesis-status` sits here; `approve-adr` sits one stage later. Don't skip straight to drafting an ADR from an untested Hypothesis.

## 2. ADR → BRD → FDD → Story order & Work Package Derivation

6. **ADR before BRD before FDD before Story, strictly.** Each cites the one before it and does not restate it. An FDD that re-derives its own ADR's reasoning instead of citing it is a sign something was drafted out of order.
7. **User Stories ARE the Work Packages for Subsidiary Plans.** Schedule (6.1) and Cost (7.1) plans cannot be front-loaded against speculative estimates; they require real duration and resource commitments. The User Stories decomposed from FDDs with testable Acceptance Criteria (BDD) *are* the PMBOK Work Packages (5.4 WBS). Once User Stories exist, they provide the real story points, velocity, and task items needed to synthesize:
   - **Scope Management Plan (5.1)**
   - **Schedule Management Plan (6.1)**
   - **Cost Management Plan (7.1)**
   - **Resource Management Plan (9.1)**
   into the integrated **Project Management Plan (4.2)**.
8. **Not every Accepted ADR produces a Story.** Confirmed twice: an ADR whose every real decision is "record a convention for future work" (no current build target) produces zero code-shaped stories, and that's the correct output, not a gap to fill by inventing one (ADPA, ADR-032/Epic 3; FDD-032 names this explicitly as "no current build target").
9. **A drafted Story can still turn out not to be code-shaped.** Running `implement-story` against it is how you find out — not by reasoning about it in advance. When that happens, reclassify (a Governance Exercise register, or equivalent), don't force a lighter-weight Story template into existence for a category of one (ADPA, Story 1.1 → GOV-EX-001).

## 3. The pipeline-entry gate

10. **`validate-intent-foundation` sits between "the documents are approved" and "it's safe to start `implement-story`."** These are genuinely different questions. A Story can have an Accepted ADR, an Accepted BRD, an Accepted FDD, and still not be the right moment to start real code — e.g., a named prerequisite elsewhere is still open. Don't treat document approval as implicit permission to start building (ADPA + SocialEngage, independently converged).
11. **This gate does not learn from aggregate statistics — it reasons per instance.** SocialEngage's own low-authority learned version of this exact decision hit a hard entropy ceiling (~42% probability) on real positive-only data and could never earn autonomy no matter how much evidence accumulated. Don't re-attempt a learned version of this specific decision; `full` authority, reasoned via a decision frame, from the start.
12. **Validate the gate itself against a deliberately-wrong case before trusting it on real ones.** A policy that only ever sees cases that should pass can't demonstrate it discriminates. Build one invented, obviously-ungrounded case (no real ADR/BRD/FDD behind it at all) and confirm it loses before registering any real episode (ADPA: the "Story 9.9" red-team case; SocialEngage: "hypothetical MongoDB ADR, correctly rejected").

## 4. Code-implementation order

13. **Worktree isolation is justified by real multi-contributor state, not assumed.** Check `git log` for actual distinct contributors before deciding whether per-story worktree isolation is worth the overhead for this project.
14. **Confirm the real base branch before the first worktree, not after a failed command.** `main` is a default assumption, not a fact — ADPA's real default branch had a project-specific name, discovered via a failed `git worktree add`.
15. **A worktree does not inherit installed dependencies.** `git worktree add` gives you the files, not `node_modules`. Confirm and fix this before the first test run, not after a confusing failure that looks like a missing-package bug.
16. **Direct-push-to-default-branch skips more than a compliance checkbox.** PR review (automated reviewers, a second pair of eyes) catches things a solo local check cannot. Even with no CI gate forcing it, prefer a real PR over a direct merge once more than one contributor exists (ADPA, corrected after Story 1.2's own direct push).
17. **A pending commit-hash placeholder needs a real backfill step.** If the implementation and its log entry must be committed together before the commit's own hash is known, the `pending` placeholder needs something — a human remembering, or a pre-commit hook — to actually resolve it, or it stays wrong forever.

## 5. Governance-mechanism-building order (meta-level)

18. **Only build a TaskPolicy where a real, repeating judgment call is already evidenced.** Every policy in this methodology's real history was built *after* hitting the same kind of decision more than once — never pre-built in anticipation. See `docs/root-cause-log.md` for exactly which real case justified each one.
19. **Declaring a policy's shape (actions, decision context) is not the same as fabricating evidence for it.** A policy can sit idle — zero episodes, baseline logits at 0.0 — once its *shape* is independently confirmed by more than one real project (see `docs/policy-shapes/`). What must never happen: running a decision against invented support/confidence numbers, or registering a fake episode. This template's own policies follow this rule: declared, idle, never fed fake data.
20. **A requires_human_approval mistake is a real, repeatable failure mode — default to `true` for any decision with a known human-approval rule, and correct down later with evidence, not the reverse.** ADPA's own `approve-adr` was built with `requires_human_approval: false` initially and had to be corrected after the resolver's own autonomy logic would have bypassed a real governance rule. Every later policy in this methodology defaulted to `true` from the start because of that one correction.

## 6. Universal Agent Artifact Quality Assurance Directives

When AI agents or subagents generate any governance document, they must adhere to these five quality invariants:

1. **Negative Scope Boundary ("What this is not yet"):**  
   Every early-stage document (Spark, Ideation, Charter) MUST explicitly declare what is intentionally excluded and deferred to downstream stages. Never collapse architecture or implementation details into an intent document.
2. **Problem-Before-Solution Discipline:**  
   Articulate the mechanical friction and organizational failure mode in concrete, unsanitized terms before introducing the capability or technical premise.
3. **Standardized PMBOK 8 / IPO Frontmatter:**  
   Every generated governance document must begin with YAML frontmatter specifying: `pmbok_edition`, `pmbok_process_group`, `pmbok_process`, `lifecycle_stage`, `governance_policy`, `inputs`, `process`, and `outputs`.
4. **Non-Duplication Principle:**  
   Never re-derive or restate the reasoning of an upstream document. ADR cites Charter/Pillars; BRD cites ADR; FDD cites BRD; Stories cite FDD; PMP subsidiary plans ingest User Story work packages.
5. **No Template Clutter:**  
   Clean up blank `*.template.md` files upon creating target documents to maintain a pristine, production-grade project documentation tree.

## 7. The chain's closed loop & empirical precedents

21. **Observation → Insight → Lesson Learned is a cross-project concern, not a per-project one to rebuild.** SocialEngage's own `resolve-kb-conflict` lives under a shared knowledge-base-ingestor agent, not under the project's own governance namespace. If a project has access to a shared knowledge base, integrate with it; don't build a project-local copy of this stage without evidence the shared one doesn't fit.
22. **Adaptation → Intent Refinement loop resolved and proven in Enterprise Work Hierarchy.** Historically open across ADPA and SocialEngage, the complete closing loop from Stage 13 raw telemetry observations through Stage 17 Adaptation Plans and Stage 18 Intent Refinements was formally achieved and codified in Enterprise Work Hierarchy (Epic 10 completion, 13 empirical observations ingested, LL-041 crystallized). The loop formally closes when refined intent feeds the subsequent Phase Spark and amends originating ADRs via fast-path governance.

## 8. Session continuity & orientation

23. **Maintain one live, non-governed "where are we" register — don't rely on reconstructing it from scattered documents each time.** Enterprise Work Hierarchy's human sponsor asked, picking the project back up, "which Phase and Stage is this at" and got it wrong on the first pass (see rule 24) because the answer had to be reconstructed from several registers instead of read off one. `registers/Project-Status-Register.template.md` exists for exactly this: current Phase, current macro Stage, last Epic completed, next Epic queued, and any out-of-loop work in flight — updated at every Step 9 breakout *and* at any natural pause, not only epic boundaries. Model/session cutoffs can happen mid-story, abruptly, without a clean announcement that a limit is close — treat updating this register as cheap, frequent insurance against that, not a formal gate.
24. **A document's own `lifecycle_stage` frontmatter is an authoring-time label, not a live position indicator — confirm against gate records, not a single document.** Enterprise Work Hierarchy's own docs independently overload "Stage 7" four different ways (BRDs say `Stage 7 (Requirement: Business)`, FDDs say `Stage 7 (Requirement: Solution)`, Epics say `Stage 7 (Requirement: Story / Work Package)`, and the PMP + subsidiary plans say `Stage 7 (Project)` — only the last matches this template's own `chain-coverage.md` definition of Stage 7). Worse, an Epic's own stamped `Stage 7` can be stale even on its own terms: by the time a human asked, Phase 2's Stage 7 (PMP) and Stage 8 (Implementation Readiness Gate) had *both* already cleared for that Epic, one stage ahead of what its frontmatter still said. Resolve "what stage are we actually at" against `Audit-Register.md`'s dated `GOV-EX-###` gate-closure entries, never a single artifact's self-declared stage.

## 9. Cross-language & cross-epic contract discipline

25. **"Node/Jest" was never accurate for every real JS/TS project — name every real variant, don't let an early shorthand harden into a wrong default.** Enterprise Work Hierarchy's real test runner is Node's native `node:test`, not Jest; this template's own `implement-story` guidance called the loop "Node/Jest-first" regardless, with Python/`pytest` footnoted as the exception. Jest, `node:test`, and `pytest` are three independently-real variants with no fixed "default" among them — state each explicitly and confirm which one a new project actually has, the same way the base branch gets confirmed, rather than assuming the first-listed one and treating the rest as edge cases.
26. **A contract suite that only runs "this epic's own tests" cannot catch the regression it exists to catch — the loop's own later step already assumed otherwise.** `heal-contract-failure`'s "Cross-epic regression (a foreign contract breaks)" section has always assumed a foreign contract *can* break during a story — which is only possible if the full suite actually runs at Step 6, not just the current epic's. The step's own wording said "the epic's contract suite," silently narrower than what the rest of the skill already depended on. Enterprise Work Hierarchy's real Step 6 runs the full glob (`node --test tests/contracts/**/*.test.js`, all areas, every time) specifically so one story's change gets checked against every other area of the project at once, not just its own — that is the generalizable rule, independent of which language/runner a project uses.
27. **The specific test framework is never the point — coverage and regression/contract-break detection are.** Stated directly by this template's own sponsor rather than inferred from an incident: it does not matter whether a project uses Jest, `node:test`, `pytest`, xUnit, or any combination, including more than one at once in a polyglot project (a Python backend and a TypeScript frontend, say) — what's load-bearing is that whatever runs actually exercises the project's contracts and reliably surfaces a break. Don't converge a polyglot project onto one framework for the sake of this loop's own tidiness; run every ecosystem's full suite at Step 6, every time (rule 26), not just the one this story happened to touch.
28. **Sequential multi-agent collision avoidance needs no new infrastructure if pickup order is already deterministic.** Raised directly by this template's own sponsor, anticipating scale before hitting it rather than after: once several agents are each running this loop concurrently, picking up the next story strictly in the pre-approved ADR→BRD→FDD→Story sequence (never an arbitrary or freely-chosen item) means there is only ever one unambiguous "next" — no contested set for two agents to race over. The collision-safety mechanism was already present and unused: `git worktree add -b feat/story-<X.Y>` against a shared local repo is itself an atomic ref creation, so the *failure* of that command (not a separate `git worktree list` pre-check, which can go stale between checking and creating) is the authoritative "someone already claimed this" signal. This explicitly does **not** solve free-for-all task bidding among agents proposing *different* work — that remains `PIL-11`'s own distinct, still-unbuilt problem (Autonomous Multi-Agent Swarm Orchestration & Competency Bidding); don't conflate the two.
29. **An existing branch is not proof of abandonment — assuming so and escalating straight to `heal-contract-failure` is its own collision.** Caught immediately after rule 28 landed, by the same sponsor: the resume-branch guard originally said "a run was already started" and jumped straight to healing, with no check for whether that run is *still live*. A second agent treating a live run as abandoned and starting to "heal" it interferes exactly as badly as two agents both starting `implement-story` on the same story. There is no mechanical liveness signal yet in this methodology (an agent mid-step may have zero commits so far; a quiet `git log` proves nothing) — ask the human when it's ambiguous, and do nothing (neither `implement-story` nor `heal-contract-failure`) until abandonment is actually confirmed.

## 10. Subsidiary plan tailoring

30. **A subsidiary plan's Foundation Pack is a project-size decision, not a universal step.** Stated directly by this template's own sponsor: Enterprise Work Hierarchy's `Schedule-Foundation-Pack` (basis-of-estimates, CPM network, activity list, Gantt, each individually gated through Stage 6.B) is real and was genuinely needed for that project's complexity, but a small project can rely on its subsidiary plan — or even the integrated PMP alone — to carry every required answer directly, with no Foundation Pack at all. Only populate one when the subsidiary plan document itself cannot hold the level of detail actually needed, not for every plan by default. Caught as a live gap: `scripts/orchestrate_pmbok.py` currently generates a "Foundation Baseline Roll-up" section expecting a pending Foundation Pack for every subsidiary plan regardless, with no branch for "this plan doesn't need one" — a project that tailors this away still has to manually remove that generated section rather than leaving a dangling "Pending" reference.
31. **A Foundation Pack, once approved, is a frozen historical basis-of-estimate record — not a living document to extend with new cross-cutting content.** When a new rule is discovered that touches scheduling/resourcing concepts (e.g. rule 28's multi-agent sequencing), it goes in the **living** subsidiary plan (`Schedule-Management-Plan.md`, etc.) as a new dated subsection, the same way that document already handles Phase 2 additions without touching its own Phase-1-locked Foundation Pack — never backdated into the Foundation Pack itself, which stays exactly as it was when its Stage 6.B gates closed.
32. **Planning-round size is a hybrid agile/waterfall tailoring decision, scaled to uncertainty — not a fixed batch size.** Stated directly by this template's own sponsor: don't try to fix every problem in one go, especially the genuinely unknown, high-uncertainty ones. Well-understood, already-evidenced work (standard algorithmic patterns, extensions of a proven pattern) can be safely batch-planned further ahead, waterfall-leaning. Genuinely novel, unevidenced work (Enterprise Work Hierarchy's own `PIL-11` competency-bidding swarm engine is the real example — flagged repeatedly across rules 28, 29 as "a distinct, still-unbuilt problem," zero real evidence anywhere in this methodology for how it should actually work) should not be pre-committed into the same upfront batch as its well-understood neighbors. The existing Stage 17/18 phase-close mechanism is sufficient to act on this — no new infrastructure needed: an already-approved Epic can simply be marked deferred to the next phase (the same pattern already used for an individual deferred Story, e.g. Kayros Bay's Story 1.1 — `Status: Deferred`, while its Epic stays `Approved`), closing the current phase around its remaining, lower-uncertainty scope rather than forcing the unknown epic to execute before its own unknowns are actually ready to be tackled.
33. **A single real outcome that diverges wildly from a plan's calibration is a data point to log, not evidence to recalibrate from.** Enterprise Work Hierarchy's Phase 1 (30 stories, 10 epics) completed in ~2 calendar days against a planned 14-week human-paced estimate — a huge divergence, but still only one phase's worth of evidence. Deriving a new "agent velocity" calibration from it would be exactly as unevidenced as the human-paced number it would replace (same discipline as rule 18: only build a TaskPolicy — or here, a calibration — where a real, *repeating* case is evidenced, never from a single instance no matter how dramatic). Log the divergence next to the original estimate in the living plan (not the Foundation Pack — see rule 31) and keep planning on the provable, conservative basis until enough real agent-execution data points actually accumulate. This is the same tailoring instinct as rule 32 applied to *duration* uncertainty rather than *scope* uncertainty: when you don't yet hold the evidence, plan generously on what you can prove, not on what one surprising result suggests might be possible.
34. **Automated dependency-bump PRs are a real, un-evidenced-as-safe third trigger for `heal-contract-failure`, not something closed on "nothing looks broken."** Enterprise Work Hierarchy's own real history: 4 Dependabot PRs, none ever run against the contract suite — attached PR-check bots (a Cursor approval/security agent) only reported `NEUTRAL`, which is not a test-suite result. Each was resolved by a human applying the bump directly and closing the PR, with no regression visible — but "no regression visible" was never the product of actually running the suite against that specific change, so it isn't verification. The fix needs no new infrastructure: treat a bump PR exactly like any other RED trigger — check out its branch, run the full accumulated suite (rule 26), then merge (GREEN) or walk the full heal loop citing the bump as cause (RED). Detection was never the missing piece (the full-suite rule already catches a bump-caused break the moment it runs); *triggering* that run automatically, or at minimum doing it deliberately before closing the PR, was.
23. **Second Brain Ingestion & Healing Toolchain Protocol.** Knowledge synthesis requires dual-locus discipline: local code repository registers (`Audit-Register.md`, test suites) must be ingested into the central Obsidian Second Brain (`06 Synthesis & Lessons Learned/OBS-*.md`, `LL-*.md`). Running `scripts/brain/heal-brain.mjs` immediately after observation authoring resolves wikilink ambiguities and prevents broken cross-project reference rot. Always run `npm run lifecycle` to mathematically verify that all 18 stages maintain 100% vertical traceability and 0 open cognition loops.
